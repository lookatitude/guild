guild.placement.v1 — one validated placement locator

A design for replacing independently-declared kind/id/layer in the S2/S3 contract surface with one authority-bound placement value — revised after an adversarial review returned REJECT on four counts, every one of which I reproduced.

Task #29 (DESIGN) Version v2 — revised after REJECT, then REJECTED AGAIN Status NOT adopted; two rounds, two rejections Base fix/s3-open-defects @ 3595ac3 Branch design/placement-locator

The pattern this document is about — a component discovered by a defect rather than by design — applied to the document itself, twice.

Both halves of that matter, and a reader who takes only the first will repeat this. It is the strongest argument for the design: the failure mode is real enough to catch its own author, mid-proposal, on the surface he was proposing to fix. It is equally the strongest argument against trusting any single draft of it — including the next one, and including this one.

Concretely: v1 was rejected, and the rejection was right. An adversarial G-spec round returned REJECT with four P1 findings. I verified all four against the live tree and one of them by execution. The direction survived review — “replacing independently declared kind/id/layer with a validated canonical placement is the right direction” — but four load-bearing specifics were wrong, including one where I misread ls skills/ and called two skills “tiers”, and one where my own correction from two commits earlier was still wrong. §12 lists every change and what forced it.

The practical consequence for whoever reads this next: this document has now been reviewed TWICE and rejected TWICE. Round 2 reviewed the revisions rather than the original objections and returned REJECT with five further P1 findings — none of them repeats from round 1. Treat every section below as a proposal with a demonstrated history of being wrong in exactly the way it warns about. §14 records what round 2 found and what it means.

2. Diagnosis: missing canonical placement plus conflated equivalence relations

function identityOf(
  kind: string, id: string, hash: string | null,
  projectId: string, layer: string
): string {
  return `${kind}\0${id}\0${hash ?? ""}\0${projectId}\0${layer}`;
}

v1 blamed one thing — an open-ended tuple of declared scalars. The review supplied the missing half, and it is the better diagnosis:

There are two causes, not one.

(a) There is no canonical locator. kind, id and layer are declared beside a path that also describes them, so they can contradict it — which is why layerAgreesWithPath had to be invented, and why the file says “a declared component that can contradict a derived one is not a component, it is a second opinion.”

(b) ONE equivalence relation is overloaded across five questions — placement, byte-state, liveness, rollback and cycle detection. A single identityOf serves all of them, so any change that makes it right for one makes it wrong for another. This is why each amendment landed cleanly and still left a hole.

Cause (b) explains something (a) alone cannot: why the amendments worked and the surface still failed. It also predicts the shape of the answer — not one better key, but the right key per question.

A third property is the mechanism behind open defect 2: hash ?? "" makes a hashless origin and an empty-hash origin the same key, so the cycle guard has nothing to seed with.

3. The proposal — placement is (root, path), bound to repository authority

interface PlacementV1 {
  schema_version: "guild.placement.v1";
  /** WHICH ROOT. Not derivable from a path — the irreducible declaration. */
  project_id: string;
  /** WHERE IN THAT ROOT. Project-root-relative, canonical, REQUIRED. */
  path: string;
}

function derivePlacement(
  p: PlacementV1,
  roots: RootRegistry,             // project_id -> rootKind.  See section 5.
  role: "live" | "historical",
  authority: PlacementAuthority,   // inventory / roster.      See section 4.
): DerivedPlacement | PlacementRefusal;   // total

interface DerivedPlacement {
  layer: DefinitionLayer;
  kind: DefinitionKind;
  tier: string | null;
}

id is NOT in DerivedPlacement, and that is a correction, not an omission. v1 claimed id derives from the path. It does not, for skills: skills/core/principles/SKILL.md has identity guild-principles, and build-inventory.ts reads it from frontmatter name:. I verified this — the inventory says guild-principles ← skills/core/principles/SKILL.md.

So id stays a declared field, and the design's honest position is: declared but validated against the file's own frontmatter — exactly the treatment layer currently gets from layerAgreesWithPath, which is the treatment v1 proposed to delete. Deriving everything was too strong a thesis; the repository does not support it.

4. The grammar, and why it must be derived rather than written

v1's grammar was wrong on the live tree in four ways, and I wrote it from ls. That is the strongest single argument in this document, because it is a demonstration rather than an assertion: a hand-written grammar is a hand-maintained tuple wearing a different hat, and it drifted from reality on its first day.

What v1's table saidWhat the tree actually holds
guild-operations, guild-quality are tiersThey are skills: skills/guild-quality/SKILL.md has id guild-quality. I misread ls skills/.
Skill files are always SKILL.mdskills/meta/using-guild/SKILL.src.md is an authored definition source and is in the inventory as using-guild.
Skill id is the directory nameIt is frontmatter name: — principles/ → guild-principles.
Six productions cover the surfaceGenerated host packages expose skills under .agents/skills/guild/** — an installed-tree layout absent entirely.

The revision: bind the grammar to the authority that already exists

The repository already has a canonical answer to “what definitions exist and what are they called”: guild.inventory.json, generated by build-inventory.ts, plus roster.ts for project-local definitions. The grammar should not restate that — it should consult it.

  • Live placements are validated against the inventory/roster, not against a hand-written table. A path is a legal live placement iff the authority lists it.
  • The source tree and the installed tree are different placement spaces and must be distinguished explicitly — skills/meta/x/SKILL.md and .agents/skills/guild/x/SKILL.md are the same definition in two spaces, and conflating them is a new wrong-bytes class waiting to happen.
  • A written table survives only as a fallback for historical paths, which by definition are not in today's inventory.

This is strictly better than v1's table on the design's own terms. v1 argued that deriving beats declaring because a declaration can contradict what the path proves. The same argument applies one level up: a hand-written grammar is a declaration about the repository, and it can contradict the repository. Binding to the inventory removes the second opinion for the same reason the first change removed it.

5. Root kind is a registry, not a scalar

v1 proposed a single per-manifest rootKind, arguing it “cannot drift entry-to-entry”. The review showed that is exactly backwards:

One manifest legitimately traverses heterogeneous roots. The cross-project case umbrella → sub-one → sub-two is pinned by an existing test. Those placements belong to a workspace root and to project roots simultaneously. A single scalar does not merely mislabel uniformly — it necessarily mislabels, because there is no single correct value.

And the manifest does not “already know” it: it carries only a top-level project_id. .guild/guild.yaml knows the current root's kind, not every referenced root's.

Revised: RootRegistry — an authority-bound project_id → rootKind map, sourced from each root's own manifest / the workspace federation record, with an unknown root refused rather than defaulted. That keeps the “no second opinion” property: root kind is looked up from the authority that owns it, never asserted by the entry that uses it.

6. Live vs historical, and why nesting must be evidence-bound

The live/historical split survived review as principled. The historical grammar did not.

Where the split came from, because the reasoning generalises. A first draft collapsed from and to into one strict type. That draft would have made open defect 3 worse: its own motivating example, .guild/agents/archive/architect.md, does not parse under a live grammar — so the historical side of a real migration becomes unrepresentable, which is a fail-closed refusal of a legitimate operation dressed up as a fix.

Catching that a proposal makes its own motivating defect worse is the check this surface most needs, and it is cheap: take the defect the design exists to fix and run it through the design. The real axis turned out not to be from vs to at all — it is live vs historical. A successor must be somewhere the system can put a definition today; a predecessor is wherever the old world left it, and the old world is not bound by today's layout.

v1 said “nesting permitted below the kind directory”. The real tree contains .claude/agents/_shared/handoff-contract.md, methodology-skills.md and plan-anchors.md — verified present. These are helper fragments, not agents, and v1's rule admits every one of them as a historical agent. It equally admits an arbitrary shadow file under .claude/agents/archive/, which is the very class the live grammar exists to refuse.

And cited_as does not save it: a citation proves what was cited, not that the cited file was ever a definition.

Revised: historical admission must be evidence-bound, by one of:

  • Versioned legacy productions — an explicit, dated list of layouts the old world actually used, which is a closed set because history does not grow; or
  • Binding to a historical registry or run record — the path is admissible because a record shows it was a definition, not because its shape is plausible.

Either way the burden inverts: a historical path is admitted on evidence, not admitted unless suspicious. Nesting alone is never evidence.

Also settled (v1 was internally underspecified — the table listed it generically, §10 proposed historical-only): templates/specialists/<id>.md is historical-only. It is read-only feedstock minted into .guild/agents/; it is a plausible migration source and never a legal successor.

7. The three equivalence relations

This section replaces v1's two-key answer, which was also wrong — and the review proved it by execution rather than argument.

A placement-keyed cycle guard breaks a legal history. Executed against the current contract:

plugin/.guild/agents/A.md@h1  →  B@h2  →  plugin/.guild/agents/A.md@h3

The current validator accepts this and resolves to A@h3; the contrast is pinned in adoption-manifest.test.ts. v1's guard records only (project_id, path), so it sees the final placement as already visited and returns ambiguous. Two genuinely different definitions do collide on one placement.

The lesson is the one from §2: PlacementV1 is a locator, not definition identity. v1 fixed the overload halfway and then reintroduced it.

RelationKeyAnswers
placement(project_id, path)Where is this? Is this move a move at all?
source(project_id, path, content_hash)Which byte-state was adopted? Fork or re-adoption (liveness)?
reachability
(cycle guard)		exact source key when the origin hash is known; a placement wildcard that conservatively matches any later byte-state at that placement when it is notHave we been here before?

The third row is the review's construction and it is better than mine: it keeps the legal A@h1 → B → A@h3 history resolving (the exact key distinguishes h1 from h3) while still giving a hashless origin something to seed with (the wildcard). Movement detection and reachability are mapped separately — they were the same question in v1, and that was the residue of the original overload.

The rule that caught this twice, stated so it can be applied a third time. Between v1 and this section the same mistake was made and corrected twice — first keying identity on placement alone, then keying only the cycle guard on it. Both were caught by one question:

A design whose headline is “stop losing identity components” cannot open by dropping one.

Run any proposed key against it: does the new key merge two things the old one told apart? Placement-only merges A@h1 and A@h2. That is a losing trade regardless of how much tidier it reads, and it is the check to apply to the next revision of this design too.

Why this is a consequence of the collapse, not an independent fix

The reachability key is only expressible because placement is complete. Under the five-scalar tuple there is no key that is both total and discriminating: the hash is discriminating but nullable, and everything else is total but too coarse. That is precisely why the seed had nothing to use, and why open defect 2 could not be fixed in place — the fix needed a component the tuple did not have. Completing placement is what makes a total key available; splitting the relations is what makes a discriminating one available at the same time.

This is the difference between the proposal being cleaner and the proposal enabling a fix that was otherwise unreachable. It is the strongest argument in the document, and it survives the REJECT unchanged.

Each relation must be assigned to its call sites explicitly as part of implementation. That enumeration is a deliverable, not an implementation detail.

10. Migration cost — not near-zero

v1 claimed migration was “close to zero”. That was true only of stored data. The contract surface is consumed structurally today: execution-transport-ports.ts defines DefinitionRefLike, carries it on spawn/pane requests, and refsConflict compares layer, kind, id, relative_path, content_hash, source_commit and every pinned skill locator field by field. I verified this. Removing or deriving those fields changes production code.

SurfaceCost
Stored adoption manifestsGenuinely zero — none exist. The .guild/runs schema hits are trace payloads containing source text, not manifest instances.
Contract source (both files)Substantial — shapes, validators, identityOf, traversal, liveness.
Transport (DefinitionRefLike, refsConflict)Real. No production producer populates the field yet, which caps the blast radius — but the comparison code is live.
Conformance, host packages, fixturesReal and broad.
Schema versionLikely a major bump on both contracts.

The “unconsumed, so pay now” argument still holds for stored data, and that is the argument that expires when a producer lands. It was overstated as a claim about the whole surface.

11. Verification requirements

A. A type check sees one type graph and no further

A structural duplicate in another module once stayed layerless with 43 assertions green. Required: a duplicate-shape rail across src/, scripts/, hooks/ and every resources/ mirror.

B. Anti-vacuity must itself be checked for vacuity

It has failed here twice: sweeps that were no-ops, and a rule with nothing to feel it (the agreement rule was added, every fixture made to comply, all five guards swept green). The procedure: build a fixture that makes every other guard pass, sweep the one under test, and confirm which line produced the rejection. Required: every production has a positive case and a near-miss differing by one segment, each asserting its specific refusal reason.

C. A deleted guard with a redundancy proof beats a kept one with a comment

layerAgreesWithPath should be deleted with its redundancy proved by enumeration — not kept as belt-and-braces.

D. The rail must walk authorities, not directories

Revised from v1, which said “walk the real definition trees”. The review is right that this would either fail on .claude/agents/_shared/** or falsely classify those fragments as definitions. Required: the rail reconciles the grammar against guild.inventory.json and the roster — the same authorities the grammar consults — so that a new definition layout fails the rail rather than silently widening the surface.

14. Round 2, and what two rejections mean

Round 2 reviewed the revisions and returned REJECT — five P1 findings, none a repeat of round 1's. The revisions fixed what round 1 found and introduced a new class of defect while doing it. That is the third demonstration, on this document, of the phenomenon the document is about.

Every round-2 P1 is about AUTHORITY

This is the useful part, because it is one theme rather than five accidents. v1 declared things that could contradict the repository. v2 replaced those declarations with authorities — and the authorities either do not exist, cannot be trusted, or cannot be populated.

#FindingStatus
P1Binding the grammar to guild.inventory.json is a trust inversion. The inventory validator checks non-empty strings and uniqueness — not that a path exists or belongs to its category. Demonstrated by forging {id:"forged-skill", source_path:".guild/agents/not-a-skill.md"} into skills[]: validateInventoryV1 returned valid: true. The generator is sound because it rebuilds from live discovery; that guarantee does not transfer to an arbitrary on-disk inventory consumed later. Installed-tree placements are not emitted at all.OPEN. Needs three explicit authority constructors (fresh source discovery; a shipped host-projection manifest; a per-root fresh roster), each carrying provenance/hash and refusing stale or absent authority.
P1The RootRegistry cannot be built from existing data. guild.yaml carries name and kind; adoption uses project_id; no rule says they are equal. The workspace record carries kind: sub-guild|sub-project, not rootKind. And the federation ADR calls workspace.json a derived, deletable projection — not a system of record.OPEN. Needs a canonical project_id in guild.root.v1, uniqueness validation, and a registry built by using federation only to locate roots then reading each root's own manifest.
P1Rollback is unmapped. §2 says the old key was overloaded across five questions; §7 supplies three relations and never assigns rollback. Rollback validity requires the named earlier edge to be reversed in both directions, still operative, LIFO/era-valid, and to restore a departed destination — a source key cannot prove any of that.OPEN, and §2 is wrong as written: rollback is not an equivalence relation at all. It needs a directed reverses(rollback, target, history) predicate, and §2 should stop counting it among the five.
P1Evidence-bound historical admission is a requirement dressed as a design. Neither proposed authority exists — no versioned legacy-production registry, no historical definition registry, and no definition references in this checkout's .guild/runs. Plus a shape contradiction: PlacementV1.path is required relative, while the historical contract deliberately requires absolute paths to preserve the literal citation.OPEN. The legacy productions must be enumerated in the spec, the evidence envelope defined, and the absolute/relative contradiction resolved — with an explicit choice for legitimate migrations whose evidence was never recorded.
P1Keeping id declared is a retreat, not a resolution. Once derivePlacement consults the authority, the authority lookup returns the id — so it can be derived even though it cannot be parsed from the path. Keeping it declared recreates the second-opinion problem the design exists to remove. There is also no uniform “frontmatter is authoritative” rule: shipped skills use frontmatter name, project skills use the directory, shipped agents use the filename stem, project agents use frontmatter with a filename fallback — four id sources.OPEN. id returns to DerivedPlacement, obtained from the selected authority. If transport must carry it, name it a redundant asserted/cache field required to equal the derived value.
P2cited_as does not exist. I referenced it as though it were a field of the current contract; the only occurrence in the repository is this spec. Also “history does not grow” is false — the set of legacy layouts grows every time a current layout is retired.OPEN. Define the field or drop both claims. The defensible property is that each dated legacy-production version is immutable after publication.
P2The “otherwise unreachable” claim is overstated. The wildcard, not placement completeness, is what makes reachability total under an unknown hash. An old-tuple wildcard was already expressible — coarser, and over-refusing more histories, but expressible.OPEN. Narrow to: adding the path makes the wildcard placement-complete and avoids false collisions for same-layer moves.

What two rejections mean, stated rather than rationalised

Round 1 found four P1s. Round 2 found five more, none of them repeats. The revisions were not sloppy — each was a direct, evidenced response to a real objection — and they still carried a fresh load-bearing defect apiece.

A design that keeps acquiring defects one review at a time is the same shape as a contract that keeps acquiring identity components one defect at a time. The document has now reproduced its own subject three times.

The conclusion this supports is about process, not content. Both rejections agree the direction is right — replacing declared kind/id/layer with a validated canonical placement — and both found the specifics wrong in a new way. Two data points is not proof, but the pattern matches the one this document was written to describe, and the honest reading is that another same-session revision by the same author is the least likely thing to converge. That is a recommendation for whoever sequences this, not a decision this document can make.

13. The decision being asked for

Adopt guild.placement.v1 as the canonical locator on both ends of an adoption hop — deriving kind and layer, validating id against frontmatter, binding the grammar and root kinds to existing repository authority, and splitting the overloaded identityOf into three named equivalence relations.

This is NOT currently adoptable, and §14 is why. Round 1's four P1s were real and were addressed; round 2 then found five more in the addressing. Nine P1 findings across two rounds, no repeats. The direction has survived both reviews; no draft of the specifics has survived one.

If adopted, implementation is its own task with its own adversarial round, sequenced after the integration settles. The residual meanwhile is unchanged and fails closed: a same-layer move is inexpressible rather than resolving to wrong bytes.

If not adopted, the expectation should be recorded explicitly: identity will acquire its next component when the next defect finds it.
